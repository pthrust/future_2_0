# Декомпозиция функционала ESB при выводе из эксплуатации

## ФЛК

| Что было в ESB | Куда уходит | Ответственный | Критерий паритета |
|---|---|---|---|
| Схемная валидация (структура, типы) | Schema Registry + продюсер/консьюмер | Домен-продюсер | 100% событий проходят контрактную валидацию |
| Бизнес-валидация (правила, справочники) | Доменный сервис (validators) или Flink-джоба для потоковых правил | Домен | Все правила покрыты тестами, ложных отказов нет |
| Пакетная валидация выгрузок | Quality-gate в batch ELT до загрузки в Lakehouse | Data Platform | Сверка с legacy даёт 0 расхождений |

## Трансформации
| Что было | Куда уходит | Ответственный |
|---|---|---|
| Потоковые map/filter/enrich | Flink / Kafka Streams | Домен-продюсер или Data Platform |
| Stateful-преобразования (окна, джойны, агрегации) | Flink с чекпоинтами | Data Platform |
| Пакетные перекладки, реконсиляция | Batch ELT (Spark/dbt) в Lakehouse | Data Platform |
| Трансформации «на лету» для легаси | ACL к Camel/DWH (нормализация до публикации события) | Интеграционная команда |

**Принцип:** трансформация перестаёт быть централизованной медиацией и становится ответственностью домена-продюсера (подготовить каноническое событие) либо потокового/пакетного движка.

## Бизнес-логика
| Что было | Куда уходит | Как проверяем |
|---|---|---|
| Оркестрация и правила домена | Доменные сервисы (commands) | E2E-сценарии домена |
| Распределённые транзакции | Саги + Outbox | Тесты на компенсации |
| Потоковые расчёты показателей | Flink | Сверка с legacy-отчётами |
| Логика дата-продукта | Продюсер data product в домене | Контракт data product |

**Принцип:** бизнес-логика не остаётся в «шине» — она либо принадлежит домену, либо реализуется как потоковая/пакетная обработка, либо выражается через события и саги.

## Паттерны надёжности
| Что было | Куда уходит |
|---|---|
| Retry / backoff | Консьюмеры + Kafka retry-топики |
| DLQ | Kafka DLQ (уже заявлен в README) — замена error-handling ESB |
| Идемпотентность | Outbox / dedup-ключи на продюсере, идемпотентные консьюмеры |
| Гарантии доставки | Семантика Kafka + Flink-чекпоинты, транзакционные продюсеры |
| Circuit breaker / bulkhead | API Gateway / service mesh для синхронных вызовов |

**Принцип:** надёжность перестаёт быть «функцией шины» и становится свойством каждого звена (продюсер → топик → консьюмер / Flink-джоба).

## Интеграционные паттерны
| Что было | Куда уходит |
|---|---|
| Request-reply | API Gateway (внешние) + Kafka request-reply (внутренние) |
| Pub-sub | Kafka + Schema Registry |
| Агрегация / разбиение | Flink или доменные сервисы |
| Компенсации | Саги (оркестрируемые/хореографические) |
| Маршрутизация | Выбор топика продюсером + консьюмер-группы |

## Сводная таблица вывода ESB
| Функция ESB | Целевой компонент | Волна вывода | Критерий паритета |
|---|---|---|---|
| Схемная валидация | Schema Registry | 1 | 100% событий валидны по контракту |
| Бизнес-ФЛК | Домен / Flink | 2 | Правила покрыты тестами |
| Потоковые трансформации | Flink | 2 | Задержка и полнота не хуже ESB |
| Пакетные трансформации | Batch ELT | 2 | 0 расхождений с legacy |
| Оркестрация | Саги / outbox | 2–3 | Сквозные сценарии проходят E2E |
| Retry / DLQ | Kafka DLQ + консьюмеры | 1 | 0 потерянных сообщений |
| Request-reply	API Gateway + Kafka | 3 | SLA синхронных вызовов не деградирует |
